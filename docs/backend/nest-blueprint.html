1. Overview

The browser keeps talking only to the Next.js web app, which acts as a backend-for-frontend (BFF) and calls the NestJS API server-to-server. The one exception is the Socket.IO WebSocket, which the browser opens directly to the API with a short-lived ticket. Everything runs locally in Docker first; the production host is chosen later.

What moves

All data access, auth, chat, social, push, GIPHY proxy and realtime. The web app keeps UI, routing, i18n (next-intl), theme and locale cookies and the PWA shell.

What goes away

Turso/libSQL, Ably, jose JWT cookies, direct DB access from Next, and the packages/db idea (the web app no longer touches the database).

What is shared

packages/contracts: Zod schemas and TypeScript types used by both apps, plus the generated API client.

Mobile readiness

Because a mobile app is planned, the API is designed as a public client-agnostic API rather than a private backend of the Next app.

  • Auth for any client: Authorization: Bearer <opaque session token>. The web BFF reads the httpOnly cookie and forwards it as Bearer; the mobile app keeps the token in secure storage (Keychain / Keystore). No cookies are required by the API.
  • Endpoints usable by mobile: POST /v1/auth/login (accepts clientName, clientKind: web | ios | android), POST /v1/auth/refresh (rotates the token and extends expiry), POST /v1/auth/logout, GET /v1/auth/sessions and DELETE /v1/auth/sessions/:id (list and revoke devices).
  • Sessions model: client_name, client_kind and last_seen_at are stored per session (see Database).
  • Realtime: Socket.IO handshake accepts auth: { token } with the same opaque token (mobile). The web uses the short-lived ticket so the long-lived token never reaches browser JavaScript.
  • Push: push_subscriptions gets a kind column (web | expo | fcm). Phase 1 ships web only; PushService dispatches by kind so Expo push or FCM is an added sender, not a rewrite.
  • Contracts: packages/contracts is framework-free (Zod + TypeScript only: no Nest, Next or Node-only imports) so a React Native / Expo app can import it; the OpenAPI client is generated for both.
  • Versioning: /v1 is a promise: additive changes only inside a version; breaking changes go to /v2 because old mobile builds stay installed. Return a X-Min-Client-Version / upgrade-required error code for forced updates.
  • CORS: not enabled by default; turn it on for specific origins only if a browser ever calls the API directly (the WebSocket origin allow-list is separate).
  • Uploads: binary endpoints accept raw or multipart bodies and return ETag so a mobile HTTP cache works.

2. Database (PostgreSQL + TypeORM)

44 tables ported one to one from db/schema.ts, each described as a TypeORM entity. Totals: 332 columns, 24 declared foreign keys, 43 new foreign keys that are only logical today, 26 indexes plus 9 unique indexes, 23 enum CHECK constraints. Plus one new table, sessions, and one new column, push_subscriptions.kind.

Cost of choosing TypeORM. db/schema.ts (about 38 KB, 44 tables) has to be rewritten as entity classes, and every query in features/*/services (written with Drizzle query builders) must be re-expressed with TypeORM repositories or QueryBuilder. There is no automated converter. Budget this in Phase 1 and 2 and add entity tests that check the generated migration against the schema below.

Conventions

  • Naming: entity classes are singular PascalCase (chat_messages becomes ChatMessage), properties camelCase, columns snake_case through SnakeNamingStrategy (typeorm-naming-strategies), so decorators below omit name except on @JoinColumn.
  • Primary keys: @PrimaryGeneratedColumn('identity', { generatedIdentity: 'ALWAYS' }) on integer. Keeps existing ids, so the data migration inserts with OVERRIDING SYSTEM VALUE and then resets sequences.
  • Enums: text + @Check rather than pgEnum / TypeORM enum. Adding a value is a one-line CHECK change instead of ALTER TYPE, which is friendlier to additive migrations. Zod in packages/contracts stays the first line of validation.
  • Foreign keys: SQLite did not enforce them (decision D10), so member delete removes rows by hand. In PG they become real FKs with explicit ON DELETE; users delete then cascades. Polymorphic user:<id> / admin:<id> keys stay text. Before adding FKs, the migration script must find orphan rows (see Phase 4).
  • FK indexes: PG does not index FK columns automatically; the generator lists the 28 that are missing and marks them proposed.
  • Relations: every FK column is declared twice, as a plain @Column id and a @ManyToOne with @JoinColumn. Services read the id column; relations are used for cascades and the few joins. Inverse @OneToMany sides are listed per entity but only add them where code navigates that way.
  • Migrations: synchronize: false. Baseline migration 0001_baseline is generated from the entities, then edited by hand to add CREATE EXTENSION unaccent, pg_trgm, the immutable_unaccent() wrapper function and the GIN trigram indexes marked "PG only". Later changes: typeorm migration:generate, review, migration:run. Keep changes additive as in CLAUDE.md.

  @Column({ type: 'text' }) name: string;
  @Column({ type: 'text', unique: true }) nameKey: string;        // login key, accent-free

Chosen for a small team, an MVP with a handful of users and a mobile client on the way: keep the structure simple enough to move fast, but put seams where change is already known (storage, push channels, realtime, mobile). Status: proposed by Claude, agreed direction pending Hoan's review.

Full example: push sender (web now, mobile later)

// push/push-sender.ts  (port)
export const PUSH_SENDERS = Symbol('PUSH_SENDERS');
export type PushKind = 'web' | 'expo' | 'fcm';
export interface PushSender {
  readonly kind: PushKind;
  send(sub: PushSubscription, msg: PushMessage): Promise<SendResult>; // 'ok' | 'gone' | 'retry'
}

// push/senders/web-push.sender.ts  (strategy, also an adapter over the web-push lib)
@Injectable()
export class WebPushSender implements PushSender {
  readonly kind = 'web' as const;
  constructor(private readonly cfg: PushConfig) {
    webpush.setVapidDetails(cfg.subject, cfg.vapidPublicKey, cfg.vapidPrivateKey); // current keys
  }
  async send(sub: PushSubscription, msg: PushMessage) {
    try {
      await webpush.sendNotification(
        { endpoint: sub.endpoint, keys: { p256dh: sub.p256dh!, auth: sub.auth! } },
        JSON.stringify(msg),
      );
      return 'ok';
    } catch (e) {
      return isGone(e) ? 'gone' : 'retry'; // 404/410 -> subscription expired
    }
  }
}

// push/push.module.ts  (register every strategy under one token)
@Module({
  providers: [
    WebPushSender,
    // later: ExpoPushSender, FcmSender
    {
      provide: PUSH_SENDERS,
      useFactory: (...senders: PushSender[]) => senders,
      inject: [WebPushSender],
    },
    PushService,
  ],
  exports: [PushService],
})
export class PushModule {}

// push/push.service.ts  (context: picks the strategy by subscription kind)
@Injectable()
export class PushService {
  private readonly byKind: Map<PushKind, PushSender>;
  constructor(
    @Inject(PUSH_SENDERS) senders: PushSender[],
    @InjectRepository(PushSubscription) private readonly subs: Repository<PushSubscription>,
  ) {
    this.byKind = new Map(senders.map((s) => [s.kind, s]));
  }

  async notify(ownerKey: string, msg: PushMessage) {
    const list = await this.subs.findBy({ ownerKey });
    await Promise.all(list.map(async (sub) => {
      const sender = this.byKind.get(sub.kind);
      if (!sender) { return; }                       // kind not enabled yet
      if ((await sender.send(sub, msg)) === 'gone') {
        await this.subs.delete(sub.id);              // same cleanup as today
      }
    }));
  }
}

// chat/chat.listeners.ts  (Chat never imports a sender; it only emits an event)
@OnEvent('chat.message.sent')
onSent(e: ChatMessageSent) {
  return this.push.notify(e.recipientKey, this.notifications.build(e)); // builder = strategy #6
}

Avoid

  • Returning TypeORM entities from controllers (leaks columns, lazy relations, breaks the mobile contract).
  • Generic repository or service base classes; they hide queries and make tests harder.
  • Request-scoped providers by default (each request rebuilds the graph); use them only where truly needed.
  • synchronize: true, eager: true relations and cascade saves across modules.
  • Business rules in guards or gateways; they belong in services and policies so HTTP and WebSocket share them.

Realtime: Ably to Socket.IO

Namespace /chat. Mobile clients connect with auth: { token } (the opaque session token). The browser first asks the BFF for a ticket (POST /v1/realtime/tickets, 60 s, single use), then connects with io(API_URL + '/chat', { auth: { ticket } }). The gateway resolves the session, joins fixed rooms, and admins join conversation rooms lazily through a subscribe event checked by PtScopeGuard (replaces the per-token Ably capability lists). Clients cannot emit message events; only typing is client-to-server. Payloads stay ids only, never text.
